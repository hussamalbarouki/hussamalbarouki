# مراقبة حسام 3.0 — Binance Spot Research

**منصة عربية Mobile-first تراقب السوق فقط ولا ترسل أي أمر شراء أو بيع.** تجمع محرك المراجحة الثلاثية من v2 مع **Shadow Maker** الجديد لتجربة صانع سوق Maker افتراضياً باستخدام بيانات Binance العامة ودفاتر الأوامر الحية والصفقات المنفذة.

> أهم نقطة: نجاح المحاكاة **لا يثبت** أن طلب Maker حقيقياً سيُنفذ في مكانه من الطابور، ولا يمكن ضمان أرباح يومية. لا توجد مفاتيح API، ولا أوامر Binance، ولا رصيد حقيقي. الصفقات والتكاليف والرصيد كلها داخل SQLite محلياً.

## تنصيب/تحديث Coolify — بدون Environment Variables

1. **New Resource → Application → Public Git Repository** بالمستودع `https://github.com/hussamalbarouki/hussamalbarouki.git` والفرع `binance-triangle-lab`.
2. Build Pack = `Dockerfile`، Base Directory = `/`، Dockerfile = `./Dockerfile`، Port = `3000`.
3. Persistent Volume باسم `hussam-data` ومسار Destination = **`/app/data`**. هذا ضروري لحفظ تسجيل الدخول، TOTP، أرشيف السجلات، وحالة المحفظة الافتراضية عبر إعادة النشر. **استخدم نفس الـVolume الحالي عند ترقية نسخة سابقة**.
4. HTTPS نطاق صالح عبر Coolify (لا تستخدم http أو شهادة غير موثوقة لإدخال كلمة السر/TOTP).
5. Deploy/Redeploy. إن كانت نسخة جديدة، افتح Runtime Logs وانسخ `FIRST RUN SETUP CODE` لتهيئة كلمة مرور لا تقل عن 12 حرفاً + تطبيق Authenticator. في التحديث الاحتفاظ بالـVolume يعني بقاء نفس كلمة المرور والتحقق الثنائي.
6. افتح **صانع السوق التجريبي**. الافتراضي `UUSDT` و50 USDT افتراضي، ورسوم Maker مفترضة 0.1% حرصاً على عدم افتراض عرض الصفر. تأكد من توفر الزوج في حسابك واستمرار أية عروض رسوم صفرية؛ **لم نتحقق من ذلك حسابياً أو آلياً**.
7. من **الإعدادات** يمكنك تغيير الزوج، الرسوم الافتراضية، المخاطر، رأس المال... إلخ مع شرح عربي تحت كل خانة. ابدأ **تجربة جديدة** من صفحة Shadow لتطبيق رأسمال/رسوم جديدة على سجل تجريبي مستقل؛ كلمة المرور وTOTP مطلوبة لإعادة التهيئة.

لا يحتاج `npm install`، لأن نسخة Node 22 تأتي بقاعدة SQLite وWebSocket المستخدمة هنا.

## ماذا يختبر Shadow Maker تحديداً؟

- `GET /api/v3/exchangeInfo` للحصول على أزواج Binance Spot والـFilters، ثم `GET /api/v3/depth?symbol=...&limit=1000` لمزامنة دفتر الأوامر.
- يستقبل `<symbol>@depth@100ms` (تحديثات الدفتر بالتسلسل U/u) و`<symbol>@aggTrade` لمعرفة التداولات التي اصطدمت بالسيولة: `m=true` يعني البائع هو المبادر ويضرب جانب bid.
- يبني دفتر أوامر محلياً؛ إذا حدثت فجوة في معرّفات الأحداث، **يرفض استمرار المحاكاة ويلغي عروضها الافتراضية** حتى إكمال التزامن من Snapshot جديد.
- يبدأ بمحفظة افتراضية 50 USDT؛ يُحوّل 50% منها افتراضياً إلى عملة الأساس بسعر **Ask مع الرسوم**، كي لا يبدأ بمخزون مجاني. يقيم قيمة ما بقي من المخزون بسعر **Bid** وليس بسعر شراء متفائل.
- يضع أوامر Maker **افتراضية فقط** على أفضل bid وask غير المتقاطعين، بعد مراعاة LOT_SIZE/PRICE_FILTER/MIN_NOTIONAL/NOTIONAL وحجم الرصيد والكمية المتاحة.
- يحاكي التأخير قبل وصول الأمر للطابور، ويسجل كمية الأوامر المعروضة عند السعر أمامه. لا يعتبر مجرد لمس السعر تنفيذاً؛ يطلب صفقات AggTrade مضادة عند السعر نفسه، ويطرح حجمها أولاً من طابور الأوامر التي كانت أمامه. لا يعتبر إلغاء أوامر الآخرين تقدماً مؤكداً.
- يدعم **تنفيذات افتراضية جزئية** وحفظ النقد والمخزون وتكلفة شراء المخزون وتقييم المحفظة وعمولات التداول المفترضة وصافي الربح الشامل، مع Guard يوقف الاختبار إذا انخفضت قيمة المحفظة عن حد الخسارة.
- حفظ SQLite: `shadow_events` و`shadow_equity` و`shadow_ledger`. يمكن عرض السجل بالأحدث، مع معلومات الشراء والبيع الافتراضية والإلغاء والخطر، وتنزيل CSV.
- محرك الثلاثية السابق لا يزال يعمل مستقلاً بالصفحات والبيانات ذاتها.

## كيفية قراءة الأرقام

| المؤشر | معناه |
|---|---|
| قيمة المحفظة | نقد USDT + العملة الافتراضية × Bid الحالي. |
| صافي ربح/خسارة | قيمة المحفظة الحالية − رأس المال التجريبي الأول؛ **يشمل الخسارة العائمة والرسوم المفترضة**. |
| المحقق في المحاكاة | أرباح وخسائر عمليات بيع افتراضية مكتملة مقابل متوسط تكلفة المخزون؛ لا يعد ربحاً حقيقياً. |
| طابور الانتظار | كمية ظاهرية عند السعر كانت أمام الأمر عند إنشائه؛ تقدير محافظ **وليس بيانات ترتيب حقيقية**. |
| تنفيذ افتراضي | trade عام معاكس عند السعر بعد وصول زمن المحاكاة + استهلاك الطابور المفترض؛ **قد لا يحصل في السوق الفعلي**. |
| 0% رسوم | مجرد افتراض يختاره المستخدم، لا نملك صلاحية فحص عمولة حسابه، ولا نؤكد استمرار أي عرض. |

### حدود صارمة للموثوقية

- لا توجد طريقة لمعرفة **الترتيب الحقيقي** لأمر غير مرسل. لذا النتائج قابلة للتحيز رغم التحفظات.
- لا يوجد تتبع لكل إلغاء وأمر جديد على مستوى فردي: عمق المستوى المجمع لا يكشف الطابور كاملاً. قد تختلف نتيجة التنفيذ، وقد يستحيل بعض ما يظهر كنظري.
- تغطية دفتر الأوامر محدودة بعمق Snapshot وتحديثات الدفتر؛ بيانات السوق متأخرة عن المطابقة وقد تأتي trade/depth بترتيب استقبال مختلف. تتطلب النتائج مقارنة واستقراراً لمدة 7–14 يوماً واختبار تنفيذ حقيقي صغير لاحقاً بعد موافقة المستخدم إن ظهرت جدوى.
- لا توجد بيانات رسوم شخصية بدون API خاص. لا تطلب المنصة أي صلاحيات Binance ولا تشارك مفاتيح.
- إذا لم يتوفر الزوج أو إذا حظر VPS الوصول لبيانات Binance، ستظهر الحالة دون محاولة التحايل على قيود المناطق.
- المحرك لا يفترض تحقيق هدف 2$ يومياً من 50$، ولا يجمع فرصاً متداخلة كأنها دخل محقق.
- جميع الأرصدة من التجربة الحالية؛ السجل يحتوي التجارب السابقة أيضاً. تغيير الإعدادات أثناء التجربة قد يجعل المقارنة الزمنية غير عادلة: ابدأ تجربة جديدة لتقييم فرضية مختلفة.
- إصلاح الإعدادات وتعديلات CSS/JS لا تمس قاعدة البيانات الموجودة؛ **لا تمسح `/app/data` عند التحديث**.

## واجهات API

`GET /healthz` فحص حياة عام. `GET /api/setup/status` حالة الإعداد. جميع المسارات التالية تتطلب Session مسجّلة:

- `GET /api/status` و`GET /api/live`: بث لوحة المتابعة.
- `GET /api/shadow/status`: حالة صانع السوق التجريبي.
- `GET /api/shadow/events?limit=50&offset=0`: سجل العروض والتجارب.
- `GET /api/shadow/equity`: عينات قيمة المحفظة.
- `GET /api/shadow/export`: تنزيل CSV.
- `POST /api/shadow/reset`: أرشفة التجربة وبدء تجربة جديدة بعد تأكيد كلمة المرور وTOTP وCSRF.
- `GET/POST /api/settings`: إعدادات كاملة مع الشروح، دون إعادة نشر Docker.

## الاختبارات

```sh
node --version      # 22 أو أحدث
npm test             # اختبارات حسابية وأمنية ومحاكاة طابور / سجلات
```

مصادر البروتوكول الرسمية: [Spot WebSocket Streams](https://developers.binance.com/en/docs/products/spot/web-socket-streams)، [Spot REST Market Data](https://developers.binance.com/en/docs/products/spot/rest-api)، [Spot filters](https://developers.binance.com/en/docs/products/spot/filters).
